# Stata 论文脚本生成器实施计划

> 关联 Spec：spec/stata-paper-script-generator/spec.md
> 创建日期：2026-03-17
> 状态：草稿

## 1. 技术方案概述

该功能采用“双端共用一套核心生成逻辑”的实现方式：网页版提供浏览器内使用体验，桌面版提供 Windows EXE 交付形态。两端共享同一套表单配置模型、字段校验规则、最近一次配置持久化协议、Stata 版本模板管理协议和 Stata 脚本模板生成引擎，避免 Web 与 EXE 版本出现功能分叉。

首版优先实现“结构化配置 -> 导入 ini 配置 -> 校验关键字段 -> 生成 Stata 脚本/说明/缺失提示 -> 保存最近一次配置 -> 管理版本模板”的闭环，不包含脚本执行和 Stata 环境联动。桌面 EXE 版本通过桌面壳复用 Web 前端，确保实现路径一致、维护成本可控。

推荐采用前端单仓结构，划分为共享核心层、Web 入口和 Desktop 入口三层。共享核心层负责研究类型定义、字段依赖关系、ini 解析、模板注册与管理、生成器模板和结果数据结构；Web 与 Desktop 仅负责宿主环境差异，如路由、文件保存、打包分发和本地文件选择能力。

首版界面与交互提示默认提供中文支持，覆盖表单标题、字段说明、导入导出提示、模板管理提示、错误提示和生成结果说明；底层配置导入导出与脚本文本保存链路应确保中文内容可稳定显示与保存。

## 2. 技术决策

### 2.1 方案选型

方案 A：Web 与 EXE 分别维护两套独立前端

- 优点：各端可完全独立优化
- 缺点：表单、校验、模板逻辑、配置持久化逻辑和模板管理逻辑重复，后续研究方法扩展成本高

方案 B：共享前端核心，Web 单独部署，Desktop 使用 Electron 进行封装

- 优点：技术栈统一，双端复用率高，Windows EXE 打包成熟，适合快速落地
- 缺点：EXE 包体偏大，桌面运行时占用相对更高

方案 C：共享前端核心，Web 单独部署，Desktop 使用 Tauri 封装

- 优点：包体更小，资源占用更低
- 缺点：需要引入 Rust 工具链，首版工程复杂度更高

最终选择：方案 B

选择理由：

- 当前需求重点是尽快形成 Web 和 Windows EXE 两种交付形态，而不是极致压缩安装包体积
- 共享 React / TypeScript 前端核心可以最快完成首版
- Electron 在 Windows EXE 打包、文件保存和桌面分发上路径成熟

### 2.2 外部依赖

- Node.js 运行时
- TypeScript
- Vite
- React
- Electron
- 表单校验库，例如 Zod
- ini 解析库
- 本地配置持久化方案，例如浏览器本地存储和桌面端本地配置文件
- 桌面打包工具，例如 electron-builder

### 2.3 内部依赖

当前仓库暂无既有业务模块，计划新增以下内部模块：

- 共享配置模型模块：研究类型、字段定义、联动规则、校验规则
- ini 配置导入模块：读取本地 ini 配置并恢复表单
- Stata 版本模板管理模块：预置模板注册、自定义模板保存、删除与选择
- 脚本生成引擎模块：根据用户配置和模板生成 .do 文本、说明文本和缺失项提示
- 配置持久化模块：保存和恢复最近一次配置
- Web 展示模块：浏览器表单页、结果页、导入、下载与复制能力
- Desktop 宿主模块：EXE 启动入口、文件保存能力、桌面构建配置

### 5.2 集成 / 场景验证标准

场景一：网页版生成面板回归脚本

- 前置条件：系统已启动 Web 开发环境
- 操作步骤：选择“面板回归”，填写因变量、自变量、控制变量、面板 ID、年份、固定效应、标准误后点击生成
- 期望结果：页面显示脚本正文、说明文本和可下载按钮
- 异常场景：缺少面板 ID 或年份时，页面阻止生成完整结果并显示缺失项

场景二：网页版导入 ini 配置

- 前置条件：系统支持首版 ini 导入结构
- 操作步骤：用户导入本地 ini 文件，等待配置被解析并映射到表单
- 期望结果：页面自动填充相关字段，并允许用户继续编辑
- 异常场景：ini 结构不合法时，页面给出明确错误提示且不影响手工填写

场景三：模板管理

- 前置条件：系统已加载预置模板
- 操作步骤：用户查看模板列表，保存一个自定义模板，再删除该模板
- 期望结果：预置模板可选不可删，自定义模板可保存可删除
- 异常场景：尝试删除预置模板时，系统阻止操作并提示原因

场景四：桌面版生成并保存脚本

- 前置条件：桌面应用可启动
- 操作步骤：在 EXE 中完成配置，点击生成，再点击保存
- 期望结果：本地生成 .do 文件和说明文件
- 异常场景：用户取消保存时，应用不崩溃且保留当前结果

场景五：最近一次配置恢复

- 前置条件：用户已在 Web 或 Desktop 端完成一次有效配置
- 操作步骤：关闭页面或应用后重新打开
- 期望结果：系统自动恢复最近一次配置
- 异常场景：配置数据损坏时，系统回退到默认空白配置并提示恢复失败

场景六：双端结果一致性验证

- 前置条件：准备同一份示例输入和同一模板选择
- 操作步骤：分别在 Web 与 Desktop 输入相同配置并生成
- 期望结果：两端脚本正文、说明文本和缺失项分析结果一致
- 异常场景：如果两端结果不一致，必须可追溯到宿主差异而非共享生成器逻辑分叉

场景七：中文界面与中文内容验证

- 前置条件：系统已完成中文文案接入，准备包含中文备注或说明的配置
- 操作步骤：在 Web 与 Desktop 中分别查看表单、导入 ini、导出当前配置并保存生成结果
- 期望结果：界面字段、按钮、提示、错误信息和结果说明均以中文显示，导入导出及保存后的中文内容不乱码
- 异常场景：若出现编码异常，系统应提示导入或保存失败原因，而不是输出损坏内容

## 6. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 首版一次支持过多研究方法 | 开发周期膨胀，模板质量下降 | 首版明确收敛到描述统计、基准回归、面板回归、DID、IV 五类方法 |
| Web 与 EXE 双端逻辑分叉 | 维护成本升高，结果不一致 | 强制共享校验器、生成器、模板管理协议和配置持久化协议，宿主层只处理差异能力 |
| ini 结构不稳定 | 导入结果不可预测 | 先定义固定 ini 键结构与版本字段，解析失败时提供回退和错误提示 |
| 模板管理规则不清 | 用户误删或覆盖模板 | 区分预置模板与用户模板，删除操作仅对用户模板开放 |
| 最近配置持久化异常 | 用户配置丢失或恢复失败 | 增加配置版本号、容错恢复和默认回退逻辑 |
| 桌面打包链路复杂 | EXE 构建延迟或失败 | 先完成 Web 闭环，再接入 Electron 打包，分阶段验收 |
| 中文内容编码不一致 | 界面、配置文件或导出结果出现乱码 | 全链路统一 UTF-8 编码，补充中文导入导出和文件保存验证 |
